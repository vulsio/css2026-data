\section{LLMを用いた一次データソースの構造化}

\subsection{課題と設計要件}

一次データソースを直接収集しようとすると2つの困難がある．
第一に\textbf{構造の不安定性}である．
HTMLは表示のための形式でスキーマがなく，提供元の改修でセレクタや表の構成が予告なく変わるため，手書きのスクレイパは修正されるまでデータ更新が止まる．
第二に\textbf{記述の多様性と欠損}である．
バージョン表記は \texttt{from 2.4.0 through 2.4.67} のような範囲，個別バージョンの列挙，\texttt{Rev.15.02.09 以前} のような自然言語が混在し，機械可読形式であっても値そのものが欠けている場合がある（6.3節）．

LLMはこの両者に適するが，そのままデータ経路に置くと前稿で確立した検知結果の再現性を損なう．
そこで次の4要件を課す．
\textbf{R1（決定性・再現性）}同一入力から常に同一の出力が得られ，過去のデータベースを再現できる．
\textbf{R2（検証可能性）}LLMの出力が機械的に検証でき，検証を通らないものはDBに入らない．
\textbf{R3（保守コストの局所化）}構造変更への追従が人手の全面的な書き換えを要しない．
\textbf{R4（監査可能性）}どのモデル・プロンプト・入力から生成された値かを追跡できる．

\subsection{P0：まず機械可読形式を探す}

LLMを適用する前に，機械可読形式が本当に存在しないかを確認する．
適切に更新され機械的に読める形式が提供されているなら，それを直接使うのが最も確実であり，LLMを介する理由はない．
実際5.6節のとおり，HTMLのみと考えていた4系統のうち2系統には，探すと機械可読形式が存在した．
残る2系統のうちAppleは構造が安定していたため後述のP2で足りた．
\textbf{LLMの適用対象は，探したうえで残ったものだけである}．

\subsection{3つの適用パターン}

機械可読形式が無いか不完全な場合に，LLMに何を出力させるかで要件R1（決定性）の満たし方が変わる．
我々は表\ref{tab:llm}の3パターンに整理した．
共通する設計は，\textbf{LLMの非決定性を日々のデータ経路から追い出す}ことである．
P1は出力を一度きりの資産として凍結し，P2は出力をコードにして日々の実行からLLMを外し，P3のみデータ経路に残るためキャッシュと検証器で決定性を作る．

\subsection{P1：欠損データの生成}

機械可読形式が提供されていても値が欠けていることがある．
Fortinet CVRFは2022年より前の \texttt{product\_statuses} が空であり，1,119件のうち465件で空であった．
CSAFは2024年以降しか存在しないため，この期間は一次データソースからは検知できない．

そこでLLMに，Fortinet自身が書いた4つの記述——アドバイザリの「Affected Products」注記と「Solutions」注記，FortinetがCNAとして公開するCVEレコード，旧来の手書きデータセット——を突き合わせさせ，補完表を生成した\cite{vdu-pr892}．
生成物はGoのリテラルとしてコミットされる凍結資産であり，日々のfetchでLLMは呼ばれない（R1）．
検証は出典間の相互照合による（R2）．
バージョン単位の照合で37件，注記中のバージョン字句の網羅検査で33件，修正版が影響範囲に含まれていないかの掃引で8件，NVDとの突合（411 CVE）で40件の不一致を検出し，個別に裁定した．
バージョン制約を持たない19行は製品全体に一致してしまうため個別に監査し，未監査の行や未知の製品名は\textbf{抽出を失敗させる}——黙って落とすことも黙って広げることもしない．
結果として465件中422件が検知条件を得て，検知条件を持つファイルは643件から1,065件になった．
裁定の根拠は生成器とその報告書に記録される（R4）．

\subsection{P2：抽出器の生成}

HTMLのみで提供されていても構造が安定していれば，抽出器のコードをLLMに書かせ，日々のfetchは生成済みコードのみで決定的に動作させられる（R1）．
7章で用いたApple Security Releases\cite{vdu-pr914}と，Microsoftの更新プログラム記事\cite{vdu-pr919}がこれにあたる．

このパターンの作業量は，構造の解析ではなく\textbf{例外の発見と確定}が占める．
Appleでは2003年以前のアーカイブ形式，公開が停止された記事，退役したホストへのリンクの扱いが大半であり，fetch・extract 合計1,327行を要した．
Microsoftでは期限切れとなった更新プログラムの継承関係をどこまで辿るかが問題となり，3,224本のリンクを調べて「系列を跨ぐのは1本だけ」という事実を確かめたうえで探索の深さを決めている．
このような網羅的な走査はLLMが得意とする作業であり，人手は生成された差分の承認に縮小される（R3）．
CIは抽出失敗率・必須フィールドの欠損率・取得件数の対前回比を監視し，閾値を超えた場合に変更後のHTMLをLLMへ与えて修正版を生成させ，ゴールデンセットへの回帰テストを通過したものだけをPull Requestとして人間のレビューに回す（R2〜R4）．

\subsection{P3：HTMLからの直接変換}

P0でもP2でも扱えないデータソースが残る．
本稿が調べた範囲で最も極端なのはOpenSSHであった．
OpenSSHは，5.4節と7.2節でFortiOSの未検知の大半を占めた組込み部品の代表であり，同時に，一次データソースから検知条件を供給するという本稿の方針が最も厳しく試される対象でもある（FortiOS自身の未検知を埋めるのはFortinetのアドバイザリであって，OpenSSHのページが担うのはOpenSSHを直接運用するホストの検知である）．
その一次データソースを読もうとすると，次の状態に行き当たる．

第一に，\textbf{項目の境界が位置にしか現れない}．
セキュリティ情報のページ\cite{openssh-sec}は55件のエントリ（日付を持つ48件と，末尾に日付を持たない7件）を持つが，各エントリは \texttt{<li>} の中で日付・影響範囲・表題・本文が \texttt{<br>} で区切られているだけで，\texttt{class} 属性も見出しも持たない．
その \texttt{<br>} の数はエントリによって2個から7個までばらつく．
何番目の断片が影響範囲かをセレクタで固定できず，抽出器を書いても表現の追加ひとつで静かにずれる．

第二に，\textbf{鍵となるCVE IDがほとんど振られていない}．
55件のうち本文にCVE IDを含むエントリは6件（ID数で7件）にとどまる．
OpenSSHはCNAではなく，我々が観測した134件のCVEはMITRE（103件）やRed Hat（22件）が採番している．
アドバイザリを書く主体とCVEレコードを書く主体が別であることが，この欠落の理由である．

第三に，詳細はプレーンテキストのリリースノートやアドバイザリに分かれる．
ページがリンクする同一ホストの文書は35件あるが，CVE IDを含むのは5件で，\texttt{Security} 節の有無自体も一定しない．
しかもその5件が挙げるIDは4件までがページ本文と重複しており，残る1件（\texttt{release-8.5} のCVE-2020-14871）はSolarisのPAMバグで，当該エントリの脆弱性ではない．
つまり\textbf{一次データソースの周辺文書を網羅的に読んでも，新たに紐付くCVE IDは1件も得られない}．
CVE IDの欠落は，文書を読み落としているのではなく，一次データソースの側に索引が存在しないことによる．

この3つが重なった結果が，5.4節で組込み部品の代表例として挙げたCVE-2024-6387（regreSSHion）である．
OpenSSHのページはこの脆弱性を \texttt{sshd(8) in Portable OpenSSH versions 8.5p1 to 9.7p1 (inclusive)} と\textbf{正確な範囲付きで記述しているが，CVE IDを書いていない}．
リリースノート9.8も同様である．
\textbf{検知条件は一次データソースだけで組み立てられるが，それが世の中で何と呼ばれている脆弱性なのかは一次データソースからは分からない}．

項目の境界が位置にしか現れず，索引も欠けているこの種のデータソースには，HTMLやテキストから \texttt{vuls-data-raw} 形式への変換自体をLLMに行わせる方が適する．
ここだけはLLMがデータ経路に残るため，出力を型で制約し，決定的検証器で検査する．
本稿で実装した検証は，各バージョン文字列が指定の解釈方法でパースできるか，範囲の上下限がそれぞれ高々1つで空でないか，出力の各バージョン文字列とCVE IDが原文に逐語で出現するか（幻覚の検出）である．
加えて変換元の \texttt{<li>} を記録ごとに保持させ，全記録を連結すると元のリストが復元されることを検査した．
CVE IDが振られていないエントリは，影響範囲と記述内容を手がかりにCVEレコードと突き合わせ，対応が付かないものはベンダ独自IDのまま収録する（本稿では3件）．

一方，決定性と監査可能性の担保は今後の課題である．
入力ハッシュから出力への対応表をモデル名・プロンプト版とともにGit管理し，同一入力には常にキャッシュを返す仕組み（R1, R4）と，対応付けが一意に定まらないものを人手レビューのキューに入れる仕組み（R2）は未実装であり，本稿では変換を手動で実行して出力をコミットすることで固定した．
これらを備えれば新規入力のみLLMを呼ぶため，日次コストは差分に比例する．

なおNVDはOpenSSHに \texttt{cpe:2.3:a:openbsd:openssh} のCPEを134件付与しており，件数では一次データソースを上回る．
\textbf{ここで一次データソースが優るのは網羅性ではなく，影響範囲の精度と，上流が「影響しない」と述べている情報である}．
逆にCVE IDによる索引はNVDにしかない．
検知条件の供給は，索引と内容のどちらか一方だけでは成立しない．

\paragraph{試作による実測．}
以上を確かめるため，P3の変換を試作し，55件のエントリをすべて \texttt{vuls-data-raw} 形式へ変換した\cite{vdu-pr928}．
CVE IDの紐付けは，一次データソースとその周辺文書だけでは6件（10.9\%）にとどまる．
これにMITREのCVEレコード183件\footnote{どのCVEがOpenSSHのものかという一覧はNVDから，レコードの内容はcve.orgから得た．cve.orgには製品による索引がなく，NVD側はCPE付与が2024年以降滞留しているため，CPE検索とキーワード検索の和集合を用いた．}を参照して39エントリに42件のIDを対応付けた結果，45件（81.8\%）まで上がった．
残る10件のうち7件は「影響しない」ことを記録するエントリでCVE IDを付けてはならないものであり，3件はCVEレコード側に該当が見つからなかったものである．
\textbf{一次データソースは影響範囲を持ちながら索引を持たず，MITREは索引を持ちながら影響範囲の精度を欠くという相補性が，実測として確認された}．

ただし\textbf{この紐付けは検知件数を1件も変えていない}．
本データソースの検知はCPE側で成立するため，条件が生成されるのは影響範囲を持つ48件であり，紐付けの前後で同じである．
検知を変えたのは，リンク先のアドバイザリが修正版を明記していた3件（例：\texttt{sshpam.adv} の \texttt{Upgrade to Portable OpenSSH 3.7.1p2}）を補った場合のみであった．
CVE IDが効くのは検知そのものではなく，他データソースや利用者の問い合わせと突き合わせるための索引としてである．

\subsection{適用方針}

表\ref{tab:sources}への適用方針は次のとおりである．
機械可読形式が提供されているFortinet，Cisco，Microsoft，およびP0で見つかったApache httpd，OpenSSLは既存の実装経路を用い，そこに欠損があればP1で補う．
Apple macOSはP2で実装済みである．
P3の対象はOpenSSHである．
\textbf{LLMをデータ経路に置く必要がある対象は，探したうえで残ったものだけであり，本稿の範囲ではOpenSSHのみであった}．
LLMは機械可読形式を置き換えるものではなく，それが存在しないか不完全な場合の補完手段として位置づける．
