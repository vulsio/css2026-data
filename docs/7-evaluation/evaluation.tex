\section{検知精度への影響の評価}
\label{sec:eval}

\ref{sec:supply}章は一次データソースの全アドバイザリを走査して検知条件そのものを比較した．
本章は製品とバージョンを10点選び，検知結果を比較する．

\subsection{実験設定}
\label{sec:setup}

同一のスキャナ\cite{vuls}に，入力データソースのみを変えた4種のデータベースを与える．\textbf{DB-primary} は一次データソース（Fortinet CVRF/CSAF，Cisco openVuln API，MicrosoftのMSRC CVRF・Security Bulletin・更新プログラムカタログ・WSUSSCN2・更新プログラム記事，Apple Security Releases，OpenSSH Security），\textbf{DB-nvd} はNVDの \texttt{configurations}，\textbf{DB-vc} はVulnCheckの独自エンリッチメント（\texttt{vcConfigurations} と \texttt{vcVulnerableCPEs}），\textbf{DB-nvd+vc} は両者である．
DB-vcにNVD由来の \texttt{configurations} は含めていない．VulnCheckが独自に何を足し何を誤るかを分離するためである．

同一のスキャン結果を4つ複製しデータベースだけを変えて検知した．対象はFortiOS 7.0.1と5.2.0，Cisco IOS 15.6(1)T1とIOS XE 16.12.1，Windows 11 23H2とWindows Server 2022，macOS 14.7.4と10.13.6，OpenSSH 8.5p1と9.6p1の10環境である．
1台に複数の製品が載るため（macOSとSafari等），検知は照合されたCPEにより製品単位に集計した（Safariの2行は本文で述べる）．
Microsoftの一次データソースのみ適用済みKBによる検知であり，スキャン結果も実機から取得した（他は宣言したCPEのみを持つ疑似サーバである）．
なお \texttt{apple:mac\_os\_x} は \texttt{apple:macos} に寄せた．NVDが古いCVEを前者に置いており，分けたままでは表記ゆれがNVDの未検知として計上されるためである．

DB-primaryが検知しDB-Xが検知しないCVEを\textbf{未検知}，逆を\textbf{過剰検知}とする．一次データソース側の誤りは過剰検知として現れる．

\paragraph{(1) C2（製品欠落）はそのまま未検知になるが，VulnCheckが埋める場合もある．}
FortiOS 5.2.0ではDB-nvdの未検知率が68.8\%（108/157件）に達し，未検知108件の93.5\%（101件）はFortinet以外が採番したCVEである．
CVE-2014-3566（POODLE）のように，Fortinetが自社製品への影響を公表しているOSS部品の脆弱性で，\ref{sec:c1c3}節でC2が100.0\%であった欠落が，長く運用されるバージョンほど累積して現れる（現行系の7.0.1では10.1\%）．
Microsoft Edgeでは逆にDB-nvdの未検知率が96.2\%で，その99.9\%はChromeが採番したCVEである．
NVDはChromiumの脆弱性に \texttt{google:chrome} のCPEしか付けず，これを取り込むEdgeを列挙しない．
DB-vcはこれを0.4\%まで下げる．
\ref{sec:c1c3}節ではVulnCheckがFortinetの組込み部品を埋めなかった．
商用エンリッチメントが組込み部品を埋めるかどうかは，製品によって一貫しない．

\paragraph{(2) 自社採番のCVEでも，NVDはAppleを大きく取りこぼす．}
macOS 14.7.4のDB-nvdの未検知率は34.2\%（462件）で，そのうち89.4\%（413件）はApple自身が採番したCVEである．\ref{sec:grain}節でAppleの付与率は99.4\%と良好であったが，CPEが当該バージョンを覆っていない．
一方で過剰検知率は0.2\%と低く，NVDは「狭すぎる」方向に誤る．同じホスト上のSafari 18.3.1では逆に過剰検知率が34.9\%と高い．

\paragraph{(3) VulnCheckの自動付与は，Windowsで大量の過剰検知を生む．}
Windows 11 23H2に対しDB-vcはDB-primaryと1件も一致せず，835件を過剰に検知した．
原因はNVDの抽象CPEの展開である．CVE-2007-1644に対しNVDは \texttt{all\_windows:abstract\_cpe} という照合不能なプレースホルダを置いているが，VulnCheckはこれを具体的な製品へ展開し \texttt{windows\_11\_23h2:-} を付与している．
2007年のWindows NT/2000のDNS脆弱性がWindows 11で検知される．
この835件のうち833件はDB-nvd+vcでも抑制されず，過剰検知率は70.6\%に達する．VulnCheckのCPEが機械的に生成されている\cite{vulncheck-cpe}ことの帰結である．

\paragraph{(4) Ciscoでは，NVDが未検知と過剰検知の両方向に外す．}
他の3ベンダではNVDの誤りは片方向に偏っていたが，Ciscoだけは両方が大きい．
しかもこの未検知は組込み部品ではなく，IOS XEの未検知80件の98.8\%（79件）はCisco自身が採番したCVEである．
原因は条件の書き方にある．NVDのCiscoのCPEは版の列挙が主体で，\texttt{cisco:ios} の67,803件の \texttt{cpeMatch} のうち範囲指定を持つものは131件にすぎない．
列挙から漏れた版はそのまま未検知になる．
過剰検知側は，NVDが余分に版を挙げた場合とCisco側が版を書いていない場合の双方を含む．後者はCisco全体に及び，CPEに対応付く1,703件のうち373件（21.9\%）は版を持つ製品名を1つも持たない．
一次データソースの側にも，版の欠落と製品の粒度という2種類の不完全さがある．

\paragraph{(5) 供給源の信頼度に基づく抑制は，正しさとは相関しない．}
Vulsは，検証済みソース（NVD等）が当該CVEに対しその製品のCPEを定義してさえいれば（バージョンが一致せず非検知であっても），補助的ソース（VulnCheck）の同一製品の検知を捨てるため，DB-nvd+vcはDB-nvdとDB-vcの和集合にならない．
macOS 10.13.6ではVulnCheckの1,554件が抑制され，そのうち781件はDB-primaryも検知している（＝真陽性を捨てている）．逆にWindows 11 23H2では，抑制されずに通った833件のうちDB-primaryと一致するものは0件であった．
この抑制規則はNVDが製品を定義しているかだけで決まるため，正しさとは独立に働く．その代償と限界は\ref{sec:limit}節で述べる．

\paragraph{(6) OpenSSHでは，一次データソースを正解とみなす前提そのものが崩れる．}
OpenSSHだけは一次データソースの検知件数がどのDBよりも少ない．8.5p1ではDB-primary 7件に対しDB-nvd 24件，DB-nvd+vc 26件，DB-vcは94件（9.6p1では5件に対し19件，22件，95件）であり，差を過剰検知と呼べない．
DB-vcだけが検知した73件の大半は，NVDが与えた版の上限をVulnCheckが落として \texttt{openbsd:openssh:-} としたもので，1999年の脆弱性が8.5p1で検知される．DB-nvd+vcで71件が抑制されるのは，(5)の規則が正しく働いた例である．
DB-nvdのみが検知した18件・15件はいずれも一次データソースに現れず，すべてMITREが採番したCVEで，8.5p1では67\%，9.6p1では80\%が2026年公開分である．
OpenSSH自身はAIによる報告の多くを現実的な脅威モデルでは影響なしと判断しており\cite{openssh-rel105}，何を脆弱性と数えるかで上流と第三者採番者の判断が割れている．どちらを正解とするかは事前に決められない．
未検知の内訳も異質である．DB-nvdの取りこぼしは各1件で，8.5p1ではCVEが採番されておらずNVDには原理的に存在し得ないエントリ（\ref{sec:c1c3}節のC1a）である．
DB-vcは8.5p1で4件，9.6p1で3件を取りこぼし，regreSSHionとTerrapinを含む．
原因はベンダ名の不一致で，VulnCheckは \texttt{openssh:openssh}，他は \texttt{openbsd:openssh} を用いる（\ref{sec:setup}節の \texttt{mac\_os\_x} と同種）．
同じ製品を指すCPEが供給源ごとに違うだけで，最も広く知られた脆弱性が検知されなくなる．

\subsection{どの時点までのNVDを信頼してよいか}
\label{sec:trust}

\ref{sec:year}節では2023年公開分までのNVDのCPE付与率は100\%であった．
しかし検知結果で見ると，macOS 10.13.6に対するDB-nvdの未検知率は2023年以前のCVEで47.6\%，2024年45.2\%，2025年37.6\%であり，古い年に絞っても改善しない．
FortiOS 5.2.0の未検知108件はすべて2023年以前のCVEである．
「CVE増加前のNVDなら信頼してよい」という仮説は成り立たない．付与率の低下は2024年以降の新しい問題だが，ここでの未検知はそれ以前から存在しており付与率では観測できない．
逆にCiscoでは新しい年ほど悪く，IOS XEに対する未検知率は2023年以前34.7\%に対し2026年は8件中8件（100\%）である．
DB-vcはこの2026年公開分を0\%まで下げており，\ref{sec:c4}節で測ったCiscoの付与遅延（NVD 中位数16日に対しVulnCheck 1日）が検知結果にそのまま現れている．

\subsection{限界と考察}
\label{sec:limit}

\paragraph{一次データソースを正解とみなす前提の限界．}
本章の未検知率・過剰検知率はDB-primaryを正解とみなした値だが，一次データソースの側にも欠落がある（\ref{sec:result}節(4)(6)）．またMicrosoftのみ検知方式が異なり（適用済みKB対CPE），他のベンダと同列には比較できない．
結果はバージョンの選び方にも強く依存し，同じFortiOSでも7.0.1では未検知率10.1\%，5.2.0では68.8\%である．
指標の側にも制約がある．表\ref{tab:match}のC2には\ref{sec:c1c3}節で述べた突合の失敗が含まれ，「自社採番か組込み部品か」の判定はNVDの \texttt{sourceIdentifier} を代理指標としている．

\paragraph{供給源の信頼度による抑制の代償と限界．}
VulnCheckのCPEは機械的に生成されるため，うまく機能するものと大量の偽陽性を生むものが混在する（\ref{sec:result}節(1)(3)(6)）．Vulsの抑制規則はこれに対する妥協である．偽陽性833件がすり抜けるのは，NVDが置いた抽象CPE（\texttt{all\_windows}）とVulnCheckが展開した具体CPE（\texttt{windows\_11\_23h2}）が別製品として扱われるためで，規則を緩めれば真陽性781件は救えるが偽陽性は悪化する．必要なのは信頼度の調整ではなく，照合不能な抽象CPEをソース側で明示的に扱うことだと考えられる．

\paragraph{LLM利用に伴うリスク．}
\ref{sec:llm}章のP1・P2は非決定性を生成時に閉じ込めるが，P3はデータ経路にLLMが残る．
\ref{sec:p3}節で述べたとおり原文に無い値の混入を止める検査を機械的に強制できておらず，\ref{sec:p1}節で相互照合により118件の不一致を検出したことは，単一の出力を信じてはならないことの裏返しでもある．
