\section{検知精度への影響の評価}
\label{sec:eval}

\ref{sec:supply}章は一次データソースの全アドバイザリを走査して検知条件そのものを比較した．
本章は製品とバージョンを10点選び，検知結果を比較する．

\subsection{実験設定}
\label{sec:setup}

同一のスキャナ\cite{vuls}に，入力データソースのみを変えた4種のデータベースを与える．\textbf{DB-primary} は一次データソース（Fortinet CVRF/CSAF，Cisco openVuln API，MicrosoftのMSRC CVRF・Security Bulletin・更新プログラムカタログ・WSUSSCN2・更新プログラム記事，Apple Security Releases，OpenSSH Security），\textbf{DB-nvd} はNVDの \texttt{configurations}，\textbf{DB-vc} はVulnCheckの独自エンリッチメント（\texttt{vcConfigurations} と \texttt{vcVulnerableCPEs}），\textbf{DB-nvd+vc} は両者である．
DB-vcにNVD由来の \texttt{configurations} は含めない．VulnCheckが独自に何を足し何を誤るかを分離するためである．

同一のスキャン結果を4つ複製しデータベースだけを変えて検知した．対象はFortiOS 7.0.1と5.2.0，Cisco IOS 15.6(1)T1とIOS XE 16.12.1，Windows 11 23H2とWindows Server 2022，macOS 14.7.4と10.13.3（系統の最終版10.13.6の手前の版），OpenSSH 8.5p1と9.6p1の10環境である．
1台に複数の製品が載るため（macOSとSafari等），検知は照合されたCPEにより製品単位に集計した（Safariは本文で述べる）．
Microsoftの一次データソースのみ適用済みKBによる検知であり，スキャン結果も実機から取得した（他は宣言したCPEのみを持つ疑似サーバである）．
なお \texttt{apple:mac\_os\_x} は \texttt{apple:macos} に寄せた．NVDが古いCVEを前者に置いており，分けたままでは表記ゆれがNVDの未検知として計上されるためである．

DB-primaryが検知しDB-Xが検知しないCVEを\textbf{未検知}，逆を\textbf{過剰検知}とする．

\paragraph{(1) C2（製品欠落）はそのまま未検知になるが，VulnCheckが埋める場合もある．}
FortiOS 5.2.0ではDB-nvdの未検知率が68.8\%（108/157件）に達し，未検知108件の93.5\%（101件）はFortinet以外が採番したCVEである．
CVE-2014-3566（POODLE）のように，Fortinetが影響を公表しているOSS部品の脆弱性であり，\ref{sec:c1c3}節でC2が100.0\%であった欠落が，長く運用される版ほど累積する（現行系の7.0.1では10.1\%）．
Microsoft Edgeでは逆にDB-nvdの未検知率が96.2\%で，その99.9\%はChromeが採番したCVEである．
NVDはChromiumの脆弱性に \texttt{google:chrome} のCPEしか付けず，これを取り込むEdgeを列挙しない．DB-vcはこれを0.4\%まで下げるが，\ref{sec:c1c3}節ではFortinetの組込み部品を埋めなかった．商用エンリッチメントが組込み部品を埋めるかは製品によって一貫しない．

\paragraph{(2) NVDはAppleに下限を書かず，過剰検知が支配的になる．}
DB-nvdの過剰検知率はmacOS 14.7.4で38.5\%（342件），10.13.3で81.5\%（1,658件）に達する一方，未検知率は6.7\%・15.3\%にとどまる．
原因は範囲の書き方で，前者は全件，後者の99.4\%が，下限を持たない \texttt{cpeMatch}（\texttt{apple:macos:*} に \texttt{versionEndExcluding} のみ）により一致する．
たとえばCVE-2025-43212はmacOS Sequoia 15.6での修正だが，上限しか書かれないため14.7.4も一致する．この書き方はAppleのCPEの14.0\%（23,164件中3,237件）にすぎないが，1件が当該系統より古い全版に一致する．
DB-vcの過剰検知率はさらに高く（49.8\%・90.0\%），10.13.3の2,572件中1,526件はNVDが書いた範囲をVulnCheckが外したものである．CVE-1999-1076ではNVDの \texttt{macos:9} が \texttt{macos:-} となり，全macOSに一致する．
付与率99.4\%（\ref{sec:grain}節）は範囲の妥当性を保証しない．同じホスト上のSafari 18.3.1では未検知16.6\%・過剰34.9\%と両方向に外す．

\paragraph{(3) VulnCheckの自動付与は，Windowsで大量の過剰検知を生む．}
Windows 11 23H2に対しDB-vcはDB-primaryと1件も一致せず，835件を過剰検知した．
原因はNVDの抽象CPEの展開である．CVE-2007-1644に対しNVDは \texttt{all\_windows:abstract\_cpe} という照合不能なプレースホルダを置くが，VulnCheckはこれを \texttt{windows\_11\_23h2:-} へ展開する．2007年のWindows NT/2000のDNS脆弱性がWindows 11で検知される．
この835件のうち833件はDB-nvd+vcでも抑制されず，過剰検知率は70.6\%に達する．VulnCheckのCPEが機械的に生成されている\cite{vulncheck-cpe}帰結である．

\paragraph{(4) Ciscoでは，NVDが未検知と過剰検知の両方向に外す．}
Ciscoだけは両方向の誤りが大きい．しかもこの未検知は組込み部品ではなく，IOS XEの未検知80件の98.8\%はCisco自身が採番したCVEである．
原因は条件の書き方にある．NVDのCiscoのCPEは版の列挙が主体で，\texttt{cisco:ios} の67,803件の \texttt{cpeMatch} のうち範囲指定は131件にすぎず，列挙から漏れた版はそのまま未検知になる．
過剰検知側は，NVDが余分に版を挙げた場合とCisco側が版を書いていない場合の双方を含む．後者はCisco全体に及び，CPEに対応付く1,703件のうち373件（21.9\%）は版を持つ製品名を1つも持たない．

\paragraph{(5) 供給源の信頼度に基づく抑制は，正しさとは相関しない．}
Vulsは，検証済みソース（NVD等）が当該CVEに対しその製品のCPEを定義してさえいれば（バージョンが一致せず非検知であっても），補助的ソース（VulnCheck）の同一製品の検知を捨てるため，DB-nvd+vcはDB-nvdとDB-vcの和集合にならない．
Cisco IOS XEでは抑制された112件のうち31件（27.7\%）をDB-primaryも検知している（＝真陽性を捨てている）．一方macOS 10.13.3では1,501件を抑制して取りこぼしは5件にとどまり，Windows 11 23H2では抑制されずに通った833件のうちDB-primaryと一致するものは0件であった．
同じ規則が製品によって正反対に働く．NVDが製品を定義しているかだけで決まり，正しさとは独立だからである．その代償と限界は\ref{sec:limit}節で述べる．

\paragraph{(6) OpenSSHでは，一次データソースを正解とみなす前提そのものが崩れる．}
OpenSSHだけは一次データソースの検知件数がどのDBよりも少ない．8.5p1ではDB-primary 7件に対しDB-nvd 24件，DB-vc 94件（9.6p1では5件に対し19件，95件）であり，差を過剰検知と呼べない．
DB-vcだけが検知した73件の大半は(2)と同じ \texttt{openbsd:openssh:-} で，1999年の脆弱性が8.5p1で検知される（DB-nvd+vcで71件が抑制されるのは(5)の規則が正しく働いた例である）．
DB-nvdのみが検知した18件・15件は一次データソースに現れず，すべてMITRE採番で，8.5p1では67\%，9.6p1では80\%が2026年公開分である．
OpenSSH自身はAIによる報告の多くを影響なしと判断しており\cite{openssh-rel105}，何を脆弱性と数えるかで上流と第三者採番者の判断が割れる．どちらを正解とするかは事前に決められない．
未検知の内訳も異質である．DB-nvdの取りこぼしは各1件で，8.5p1のそれはCVE未採番でNVDには原理的に存在し得ない（\ref{sec:c1c3}節のC1a）．DB-vcは8.5p1で4件，9.6p1で3件を取りこぼし，regreSSHionとTerrapinを含む．
原因はベンダ名の不一致で，VulnCheckは \texttt{openssh:openssh}，他は \texttt{openbsd:openssh} を用いる（\ref{sec:setup}節の \texttt{mac\_os\_x} と同種）．同じ製品を指すCPEが供給源ごとに違うだけで，最も広く知られた脆弱性が検知されなくなる．

\subsection{どの時点までのNVDを信頼してよいか}
\label{sec:trust}

\ref{sec:year}節では2023年公開分までのNVDのCPE付与率は100\%であった．
しかし検知結果はそれを裏切る．FortiOS 5.2.0の未検知108件（68.8\%）はすべて2023年以前のCVEであり，Cisco IOSでも2023年以前の未検知率は56.0\%である．
macOS 10.13.3は基準445件がすべて2023年以前だが，そこでの誤りは未検知（15.3\%）ではなく過剰検知（81.5\%）として現れる．
古い年ほど条件が整うのではなく誤り方が変わるだけで，「CVE増加前のNVDなら信頼してよい」という仮説は成り立たない．付与率の低下は2024年以降の新しい問題だが，ここでの誤りはそれ以前から存在しており付与率では観測できない．
逆にCiscoでは新しい年ほど悪く，IOS XEに対する未検知率は2023年以前34.7\%に対し2026年は8件中8件（100\%）である．
DB-vcはこの2026年公開分を0\%まで下げており，\ref{sec:c4}節で測ったCiscoの付与遅延（NVD 中位数16日に対しVulnCheck 1日）が検知結果にそのまま現れている．

\subsection{限界と考察}
\label{sec:limit}

\paragraph{一次データソースを正解とみなす前提の限界．}
本章の未検知率・過剰検知率はDB-primaryを正解とみなした値だが，一次データソース側にも欠落がある（\ref{sec:result}節(4)(6)）．macOS 10.13.3の過剰検知1,658件のうち425件はAppleのアドバイザリに現れず，Apple側の欠落の可能性を排除できない．また\ref{sec:setup}節のとおりMicrosoftのみ検知方式が異なる．
結果はバージョンの選び方にも依存し，同じFortiOSでも未検知率は7.0.1で10.1\%，5.2.0で68.8\%である．
指標にも制約があり，表\ref{tab:match}のC2には\ref{sec:c1c3}節の突合の失敗が含まれ，「自社採番か組込み部品か」の判定はNVDの \texttt{sourceIdentifier} を代理指標としている．

\paragraph{供給源の信頼度による抑制の代償と限界．}
VulnCheckのCPEは機械的に生成されるため，うまく機能するものと大量の偽陽性を生むものが混在する（\ref{sec:result}節(1)(3)(6)）．Vulsの抑制規則はこれに対する妥協である．偽陽性833件がすり抜けるのは，NVDの抽象CPE（\texttt{all\_windows}）とVulnCheckが展開した具体CPE（\texttt{windows\_11\_23h2}）が別製品として扱われるためで，規則を緩めれば真陽性31件は救えるが偽陽性は悪化する．必要なのは信頼度の調整ではなく，照合不能な抽象CPEをソース側で明示的に扱うことである．

\paragraph{LLM利用に伴うリスク．}
\ref{sec:llm}章のP1・P2は非決定性を生成時に閉じ込めるが，P3はデータ経路にLLMが残る．\ref{sec:p3}節のとおり原文に無い値の混入を止める検査を機械的に強制できておらず，\ref{sec:p1}節で118件の不一致を検出したことは，単一の出力を信じてはならないことの裏返しでもある．
